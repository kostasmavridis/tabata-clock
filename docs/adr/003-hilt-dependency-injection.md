# ADR-003: Hilt for Dependency Injection

**Date:** 2026-05-17  
**Status:** Accepted  
**Deciders:** @kostasmavridis  
**Tags:** architecture, di, hilt

---

## Context

`TabataViewModel` depends on three collaborators:

1. `ISettingsRepository` — reads/writes user settings from DataStore
2. `ISoundManager` — plays audio cues via `SoundPool`
3. `ServiceNotifier` — starts/stops `TabataForegroundService`

Without dependency injection, the ViewModel would construct these directly, making it impossible to substitute test doubles. The options were:

| Approach | Boilerplate | Testability | Android integration |
|---|---|---|---|
| Manual DI (constructor params + factory) | High | Good | Manual `ViewModelProvider.Factory` |
| Koin | Low | Good | Good | 
| **Hilt** | Medium (annotation-driven) | Excellent | First-class `@HiltViewModel` support |
| Dagger 2 (bare) | Very high | Excellent | Requires manual component wiring |

Hilt is Dagger 2 with opinionated Android component wiring built in — it generates `ViewModelProvider.Factory` implementations automatically via `@HiltViewModel`, integrates with `Application`, `Activity`, and `Service` scopes out of the box, and is the architecture officially recommended by Google for Android.

## Decision

Use **Hilt** for dependency injection with the following structure:

```
SingletonComponent  (AppModule)
├── ISettingsRepository  →  SettingsRepository      (@Singleton)
├── ISoundManager        →  SoundManager            (@Singleton)
└── ServiceNotifier      →  IntentServiceNotifier   (@Singleton)

ViewModelComponent  (auto-generated by @HiltViewModel)
└── TabataViewModel  receives all three above
```

Test doubles are provided by binding `NoOpServiceNotifier` directly in the `TabataViewModel` constructor default parameter — no Hilt test module needed for unit tests.

## Consequences

### Positive
- `@HiltViewModel` eliminates all `ViewModelProvider.Factory` boilerplate
- Interface-based dependencies (`ISettingsRepository`, `ISoundManager`, `ServiceNotifier`) allow full replacement with fakes in unit tests
- Singleton scoping ensures one `SoundPool` instance and one DataStore instance across the app lifetime
- `@ApplicationContext` qualifier in `AppModule` avoids `Activity` context leaks

### Negative
- Hilt adds KSP annotation processing to the build — increases incremental build time slightly
- `@HiltViewModel` requires `@AndroidEntryPoint` on the host `Activity` — one extra annotation on `MainActivity`
- Hilt and KSP versions must stay aligned with the Kotlin version (see ADR-007)

### Mitigations
- KSP is faster than KAPT — build overhead is minimal
- The `hilt` Dependabot group ensures `hilt-android` and `hilt-navigation-compose` are always bumped together

## Alternatives Considered

### Manual DI with a `ViewModelFactory`
Viable for a small app, but requires a hand-written factory and manual wiring at every injection site. Scales poorly as the number of collaborators grows.

### Koin
Service-locator based — dependencies are resolved at runtime rather than compile time. Errors surface as runtime crashes rather than build failures. Hilt's compile-time validation is strongly preferred.

### Dagger 2 (without Hilt)
Requires explicit `@Component` and `@Subcomponent` definitions and manual `ViewModelProvider.Factory` implementations. Hilt provides all of this automatically.
